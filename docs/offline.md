# Offline board

The React/Vinext application and shared Cloudflare D1 board remain in place. Browser IndexedDB now stores a separate record per `[userId, boardId]`: last server snapshot/revision, a durable queue, recoverable editor drafts and a legacy backup when it cannot safely be migrated.

## Commit and sync contract

1. UI changes are optimistic. IndexedDB commits before any request may send them. Pending writes are reported separately; a storage failure stops editing/sync and offers a JSON export (including the open draft).
2. Consecutive unsent changes are coalesced when their baselines match. Once a request can be sent its UUID and payload are immutable. Subsequent edits remain behind it.
3. `/api/board/sync` checks live membership plus expected user/board, compares base/local/server by stable task IDs and individual fields, and updates the shared board using revision CAS. A task's cloud/focus/origin form one atomic field. Different tasks and fields merge. Same-field or delete/edit conflicts keep both values until explicitly resolved. Concurrent insertions retain all IDs; competing reorderings require a choice.
4. A D1 `batch` writes the receipt and board atomically. Retries after a lost response return the current board without applying the same operation twice. UUID reuse with different content or actor is rejected. Receipts are retained; do not prune them without a client replay-retention protocol.
5. Editor saves compare against their opening snapshot so unrelated incoming changes are retained. Drafts are local until Done; Cancel removes the draft. On reopening, the latest draft is recovered without focusing a text input. Other drafts remain in the recovery export.
6. API polling runs every 30 seconds while visible and on focus/reconnection. Background synchronization while the browser/PWA is closed is not promised. Legacy whole-board PUT and the one-time import endpoint still use CAS and can coexist during rollout.
7. Saving, pending edits, offline operation, slow connections and retries show no automatic status banner. Only errors and conflicts appear above the board; detailed sync status remains available by tapping the avatar. Each network request is bounded at 20 seconds. After successful recovery the error disappears. Network failures, request timeouts and HTTP errors have distinct visible messages and retain pending edits. The Retry action and the online event make an actual network request even if the browser's offline flag is stale; if a request is already busy, they coalesce into one follow-up attempt. HTML 5xx responses are server failures, not sign-out events.

Wire payloads currently include the base and local snapshots (8 MB request bound), not a normalized per-row database. The server derives field deltas. This favors compatibility and verifiable recovery over bandwidth optimization. Future optimization may encode the same semantics as compact patches.

## Offline shell

`postbuild` enumerates the actual built `_next/static` bundle and writes `offline-assets.json`. After authenticated board loading and three idle seconds with no queued writes, error or sync in progress, the service worker downloads static dependencies sequentially and then the generic root HTML. A previously completed bundle only needs the small manifest version check. A cache is ready only after all downloads validate. The root SSR contains no board data. API, MCP, admin and authentication responses are never cached. Root navigation serves the complete cached shell first, without waiting for the network. The client restores the last allowed account's IndexedDB snapshot, queued edits and drafts before starting authentication/sync in the background. Known offline requests fail immediately; a stalled request cannot block the restored board. No forced reload or skipWaiting interrupts an open editor. After online authentication, preparation downloads the latest complete bundle for the next launch. Previous complete caches remain for safe rollback/update.

The HTTP cache contains presentation assets only. Account data is partitioned in IndexedDB. A 401/403 or explicit logout locks the cached account and clears the active pointer. If background validation discovers a different account, the cached view is cleared and locked, and the user must reload for the new account; the old account's queued changes are never sent to it. First use on each device/browser/home-screen installation requires online authentication and preparation. Server authorization is always rechecked before syncing; until it responds, the device can show the last allowed account's local data, just as it does offline. Browser storage removal also removes local-only drafts and queued edits.

## Verification

Run `npx tsc --noEmit`, `node --experimental-strip-types --test tests/*.test.mjs` and `npm run build`. Tests cover merge conflicts, stable moves/order/blank tasks, SQL receipt replay, auth/role boundaries, cold reload with a durable store, concurrent tabs, drafts, quota failure and service worker caching exclusions. Service worker behavior uses a simulated network/cache harness; it is not an iOS Safari device test. Before relying on offline for travel, perform a first real-device online preparation and airplane-mode reopen/edit/reconnect check.

## Weak-network transport

- GET sends the last durable revision plus the expected account. Live authentication still runs; an unchanged response contains only session/revision. A different account never qualifies for this response.
- New unsealed queue entries whose base matches the confirmed revision use a structural delta: changed fields only. Its wire revision is persisted when sealing; a lost response/reload retries the same UUID and payload. Old sealed queues keep the legacy full-snapshot protocol.
- Delta writes require exact server revision CAS and use the same atomic SQL receipt/board transaction. A stale revision makes no write: return the current snapshot, rotate the local operation UUID and use the original base/local snapshots for three-way merging. Conflicts remain explicit. No new database migration or task data migration is required.
- Successful writes normally return a small acknowledgement tied to operation UUID and account. The rare full-snapshot fallback uses gzip when supported, with an 8 MB decoded-body bound. A lost response may return a complete current snapshot on receipt replay.
- Failed background attempts back off approximately 5, 10, 20, 40, then 60 seconds with jitter. Focus, polling and edits respect the delay. Manual Retry and network reconnection can bypass it; requests remain single-flight. Each pass sends at most four queued operations and yields after eight seconds between requests. Local editing is independent of network progress.
- Synthetic 810-task rich-description fixture: one checkbox was 2,021,663 bytes as two snapshots, 252 bytes as a delta; the compressed legacy fallback was 33,729 bytes. This measures payload size, not actual iPhone/LTE latency.
